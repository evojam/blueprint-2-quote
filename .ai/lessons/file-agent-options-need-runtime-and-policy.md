# Carry file-agent options through runtime and policy generation

**Context**: `@open-mercato/enterprise` 0.8.0 parses `files` and `filesBash` and supports them in the OpenCode runner, but `@open-mercato/cli` 0.8.0 omits `files` from `file-agents.generated.ts`. The generated runtime registration therefore loses staging/capture even though `AGENT.md` opted in. OpenCode 0.8 also flattens legacy `tools` and granular `permission` rules in a fixed order: a global `read: true` can be ordered before an agent's `"*": false`, leaving the built-in read tool denied even when later path rules allow the workspace. The HTTP MCP adapter accepts only top-level object JSON schemas.

**Problem**: Verifying only source frontmatter gives false confidence. Runtime staging/capture depends on `AgentRegistryEntry.files`; OpenCode access depends independently on the effective generated rule order; and an object-shaped MCP schema is required before the tool even appears. A host-side workspace fallback can bake the wrong path into a container policy, while workspace-wide read access lets a model bypass a server-side attachment-cardinality gate. Pre-registering only a fallback entry makes the generated loader skip the complete descriptor, silently dropping `sourceFiles`, `tokenUsage`, and `outcomeSchema`; importing that server-only workaround from `src/modules.ts` or module metadata also pulls Node-only orchestration dependencies into the client build. A post-generation hardener that always rewrites generated policy or deletes a cached bundle can trigger an endless development regeneration loop.

**Rule**: After generation, verify runtime registration, generated source metadata, the MCP `tools/list` shape, and OpenCode's effective agent permissions—not only authored YAML. When the installed generator drops options, invoke the app-owned registration from a server-only module `di.ts` hook and merge the complete generated descriptor before adding `files`; never import the registration from client-reachable module metadata or `src/modules.ts`. Keep the post-generation policy hardener idempotent and pinned to the container root; write only changed policy and invalidate a cached bundle only while its source is newer. Keep built-in file tools globally denied so a file agent's explicit `read: true` follows its legacy wildcard deny, then allow only server-authored analysis paths and deny `write`, `edit`, `bash`, unused skill runners, and subagents. Treat generated OCR sidecars as companions of their source PDF rather than extra attachments, but count multiple source PDFs before the model can read anything. Serialize leases, wipe on release, and make a scoped MCP tool validate and atomically author every output. Remove the workaround when the installed versions preserve the fields end to end.

**Semantic finalization addendum**: A syntactically valid model manifest can still violate cross-field invariants. Generic finalizer errors strand an otherwise correct run, while first-error-only validation forces repeated guess-and-check calls. Aggregate controlled semantic violations into one bounded response, state the same invariants in the agent prompt, and allow exactly one corrected finalization against the existing server-owned inspection. Keep the established failure code and artifact schema. Artifact agents must also show the complete `submit_outcome` discriminator and paths in `OUTCOME.md`; use a non-JSON fence for value examples because the generator interprets the first fenced `json` object as a JSON Schema.

**Tool-minimization addendum**: A deterministic server-owned file processor does not need a built-in filesystem tool merely because it receives staged files. Do not grant `read` for an unused scratch directory: models can select it instead of the scoped processor, receive a policy denial, and exit without `submit_outcome`. Expose only the processor and terminal outcome tool; make the required processor call the first instruction.

**Artifact-limit addendum**: AgentResult references and filesystem-captured files are separate bounded planes. In installed Agent Orchestrator 0.8.0, `AgentResult.artifacts` accepts at most 20 references while the collector can be configured for more files. For a larger deterministic set, keep the result within its cap by referencing strict server-owned control files, write a contiguous non-semantic inventory for the remaining files, and treat tenant/organization/run-scoped `AgentRunArtifact` rows as authoritative only after the synchronous invocation returns. Before downstream work, strict-parse the controls and require the exact captured filename set, MIME types, sizes, hashes, and retrievable bytes; run success alone is insufficient.

**Development reload**: The standalone MCP HTTP process retains its imported AI-tool bundle, OpenCode retains generated agent profiles, and Enterprise 0.8 retains native-agent registry entries across Next.js HMR while rejecting duplicate IDs. Regeneration and a Next.js restart do not refresh the standalone processes. After changing an app-owned tool or file-agent prompt, restart MCP and OpenCode before evaluating a new trace; then verify the ESM app-module bundle and generated profile contain the new contract. For app-owned native agents, make registration refresh the existing registry entry and rebuild the `AiAgentDefinition` on HMR without widening tools, scope, or mutation policy.

**Provider-protocol addendum**: `OM_AI_PROVIDER` selects the transport adapter, not the model vendor; a Claude model routed through LiteLLM must remain on the `litellm` provider unless the gateway exposes the Anthropic Messages protocol. Probe both plain generation and a forced tool call before changing configuration. A LiteLLM `/responses` call can return HTTP 200 and syntactically valid JSON while its tool-call object still violates the AI SDK Responses schema. When `/chat/completions` accepts the same call, register an app-owned Chat Completions compatibility provider after the built-in registry bootstrap, preserving the original provider metadata and env resolution; remove the override when the installed adapter makes the protocol selectable.

**Candidate-retrieval addendum**: Do not require a catalog matcher to send an entire source sentence verbatim to token search. Measurements, locations, and inflected action forms can push the exact-token threshold past a valid catalog title even when the full text is strong ranking evidence. Probe the same trusted scope with the raw sentence and a normalized catalog term to identify this failure. Keep one bounded search over 1–4 normalized product/service terms, rank against the complete original text, and keep the returned IDs as the hard grounding boundary; do not hide low recall by listing an unfiltered catalog page.

**Image-vision addendum**: A successful OpenCode `read` call for a PNG proves path access, not that the selected model received image pixels. Prove image capability with a real run. When it does not, use a bounded server-owned vision tool that derives the active workspace from trusted session context, validates one image by byte signature/size, and sends a data URL under a strict schema. The generated DI ESM bundle can remain stale even when its transitive app service changes; invalidate both the bundle and its cache when either `di.ts` or that service is newer. In local development the standalone sidecar can also inherit empty/default AI variables instead of the repo `.env`; load an existing local env file only as a documented hackathon fallback, while production still fails closed without process credentials.

**Workflow-input addendum**: An `INVOKE_AGENT` activity receives only its interpolated `config.input`; it does not implicitly inherit the workflow context. A process may carry `__files.attachments` while the file agent stages zero inputs if its activity uses `input: {}`. Pass the envelope explicitly as `__files: '{{context.__files}}'`; a standalone token preserves the object type. Assert that mapping in the code-workflow definition test.

**Artifact-persistence addendum**: A successful OpenCode `finalize` writes only the shared workspace. The runner creates durable `AgentRunArtifact` rows only after encrypted upload through the scoped `storage_s3` provider; without the enabled module, configured credentials, and reachable bucket, capture deliberately records no artifact. Before a downstream stage reads a file, verify the run's artifacts API contains it, not only the tool trace's output path.

**Workflow artifact-handoff addendum**: A captured file-agent output is an `AgentRunArtifact`, while a downstream file agent's reserved `__files.attachments` input accepts Attachment IDs. A workflow result descriptor is therefore not a file handoff. Capture the persisted run ID, list artifacts in trusted tenant/organization scope, accept only tool-authored manifest members with strict filename/MIME/byte validation, and materialize a scoped temporary Attachment through one idempotent app-owned adapter before invoking the next file agent. Checkpoint run/artifact/Attachment IDs so retry reloads completed stages. Do not call the installed proposal-only artifact-promotion command unless an approved Agent Proposal actually exists.

**Durable stage-retry addendum**: An `AgentRunSession` row is correlation state, not a heartbeat; a crashed runner can leave `pending` forever. Give every logical stage attempt a server-owned hard deadline. Before replacing a timed-out attempt, lock and re-read the scoped operation, run, and linked session rows in one transaction; terminal success wins, otherwise expire orphanable session rows and advance the logical attempt exactly once. Never perform an unconditional fail command after an unlocked `running` read. A late result stays trace data and must not replace the one attempt accepted in the business checkpoint.

**File-agent retirement addendum**: Removing an agent requires more than deleting its authored folder. Remove its generated-profile hardener entry, app-owned descriptor/file-plane registration, exported ID, and every server-tool authorization branch that admits that ID; then regenerate rather than editing generated descriptors or OpenCode profiles. Preserve shared hardening tests under a capability-oriented name, and verify the retired ID is absent from the runtime registry while supported agents retain their scope and permissions.

**Rebase-before-orchestration addendum**: Before designing a new Process Definition, workflow ID, or custom execution bridge around file agents, rebase onto the current base and inspect the app-owned workflow registry. If a code workflow already owns the trigger and earlier agent stages, extend that stable graph and its workflow-safe command convention instead of introducing a parallel orchestrator. Also check whether a database-backed definition shadows the code workflow; stop and reconcile it rather than shipping code steps that the runtime will ignore.

**Process-projection addendum**: An Agent Orchestrator `ProcessDefinition` that points at a code workflow is a discoverability/manual-start projection, not a Workflows `workflow_definitions` override. Reuse the scoped projection when extending its workflow, keep its repo-owned description and triggers accurate, and preserve operator-owned milestones/UI metadata. Existing organizations are not automatically reseeded: inspect Studio edits before an explicit forced reconciliation. Continue to check core Workflow definitions separately because only they can shadow the code graph.
**Applies to**: Agent Orchestrator file agents, `.mercato/generated/file-agents.generated.ts`, `docker/opencode/agents/*.md`, and app-owned generation scripts.
